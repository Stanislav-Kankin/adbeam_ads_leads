# adbeam_ads_leads — контекст проекта

Проект выделен из `c:\dev\prod\adbeam_wb_marketguru_parser` (WB-парсер ИНН). Решение принято 12.11.2026.
WB-парсер **не трогаем**, он остаётся отдельным инструментом и одним из поставщиков ИНН.

## Зачем проект (бизнес-контекст)

- Клиенты агентства отваливаются. Позиция руководителя (Никитин): рынок поделён, новых клиентов после 2022 почти нет, значит надо **забирать клиентов у других агентств**.
- Идея Станислава: не заменять текущее агентство, а **идти в параллель**. Три типовых сценария лидов (опыт Сайткрафта):
  1. Всё устраивает, но нужен свежий взгляд со стороны.
  2. Подрядчик не устраивает: запускаем второго параллельно и по итогам квартала или полугода выбираем одного.
  3. Только заходят в Директ и сразу хотят сравнить нескольких подрядчиков.
- Так работают крупные компании с бюджетами. Мелкие (оборот 200–400 млн) такое обычно не тянут.
- Прецедент: клиент 2017–2020 зашёл через Google Ads сбоку от основного агентства. Увидел результат в 2 раза лучше и отдал нам Директ.
- Ниши для старта: КРУПНАЯ БЫТОВАЯ ТЕХНИКА, САНТЕХНИКА, МЕБЕЛЬ (там выше вероятность своего сайта и выше чек). Первая ниша — **сантехника**.

## Пайплайн (предложение руководителя)

1. Ниша → набор коммерческих запросов (например «купить кран hansgrohe», Москва lr=213).
2. Собираем **домены рекламодателей** из рекламной выдачи Яндекса.
3. Домен → ИНН (реквизиты на сайте).
4. ИНН → Контур.Фокус / Контур.Поиск клиентов: выручка, ЛПР, контакты.
5. Таблица-досье по образцу таблицы 2019 года: подробный профиль компании, а не список почт. Её можно заполнять через Claude + Google Sheets (коннектор пока не авторизован).
6. Гайд или исследование ниши.
7. Выходим на ЛПР с документом («приготовил для вас вкусненькое») → аудит → параллельный тест.

## Ограничения из стратегии агентства (учитывать в оффере и в полях досье)

- В стратегии есть ICP №4 «производители после неудачного агентства» (аудит → перезапуск → масштабирование). Параллельный тест снимает главный барьер: клиенту не нужно расставаться с текущим подрядчиком.
- Персоны: П1 — собственник (боится, что его «разведут»; в тесте не рискует), П2 — ecom-директор (в тесте он судья, а не проверяемый; но если агентство выбирал он, может воспринять тест как проверку своего выбора). Решение принимают несколько человек, цикл сделки длинный.
- CTA «бесплатный аудит» **не использовать**. Изучение кабинетов подаём как платный или квалифицированный этап.
- Риски теста: два подрядчика на одном сайте толкаются в одном аукционе Директа, поэтому нужна схема деления (категории, гео, типы кампаний; уточнить у Димы). Нужна атрибуция (сквозная аналитика). Чек за тестовый квартал (на части бюджета) обсудить с Андреем.
- Каналы-гипотезы: outbound с оффером «запустим в параллель на одной категории, сравните по ДРР», тендеры (компании уже готовы сравнивать подрядчиков), посадочная «второй подрядчик» + Вордстат по запросам вроде «сменить агентство директ».
- Открытый вопрос к Шестакову: откуда в Сайткрафте приходили лиды на АБ-тест (сайт, реклама, тендеры, рекомендации).

## Архитектура (согласовано)

Одна основная сущность — **компания-рекламодатель** (ключ: домен + ИНН). Несколько входов, одна общая обработка.

**Входы:**
- Рекламная выдача Яндекса по запросам ниши. Либо сервис с данными по контекстной рекламе (Keys.so / SpyWords и подобные: рекламодатели по запросам, история, оценка бюджета).
- Реестр ИНН из WB-парсера (категории КБТ / сантехника / мебель): «есть ли сайт → рекламируется ли».
- Позже, возможно, тендеры на контекстную рекламу.

**Обработка:**
- Сайт → ИНН, юрлицо, email, телефон, соцсети.
- Сигналы рекламы с сайта: Метрика, тег Google Ads `AW-…`, пиксели VK / myTarget. Это не доказательство Директа, но хороший первый фильтр.
- **Сигналы сквозной аналитики и коллтрекинга**: Roistat, Calltouch, CoMagic, Callibri, Mango. Отвечают на вопрос «как будете сравнивать подрядчиков», сильный признак для квалификации.
- Ширина каталога и число категорий: подсказка, как делить Директ между подрядчиками.
- Отсев маркетплейсов и агрегаторов, дедуп по домену и ИНН.
- Склейка с выгрузкой Контура.

**Выход:** таблица-досье (Excel, позже Google Sheets) + сводка по нише (кто рекламируется, по каким запросам, тексты объявлений и офферы) как материал для исследования.

Стек как в старом проекте: Python 3.12, httpx, selectolax, Playwright, pydantic, openpyxl, tldextract. Пользователь работает на Windows / PowerShell.

## Принятые решения (12.11.2026)

- Воронка по Никитину: исследование ниши → **аудит → A/B-тест** (аудит идёт раньше теста).
- **Источник рекламодателей: Keys.so, тариф «Профессиональный»** (оплачивается, 3 мес.). SpyWords не берём.
  - Есть API: 50 000 запросов в сутки, до 500 результатов на запрос.
  - Анализ фраз и доменов: 3 000 в сутки. «Доля конкурентов по фразам»: до 3 000 строк.
  - **«Пакетный анализ»**: до 1 000 доменов за запуск, 100 запусков в сутки (750 в месяц). Этим проверяем реестр доменов из WB («рекламируется ли»).
  - «Онлайн-парсер выдачи»: 100 тыс. фраз в месяц. Если он сохраняет рекламные блоки, свой парсер Яндекса на Playwright не нужен.
  - Онлайн-парсер Вордстат: 100 тыс. фраз в месяц, для сбора запросов ниши. Пользователей 3.
  - **Проверить после оплаты:** есть ли в отчёте домена и фразы контекстная реклама Яндекса (поиск, а не только РСЯ), то есть объявления и рекламодатели по фразе; сохраняет ли парсер выдачи спецразмещение. От этого зависит схема данных.
- **ИНН → данные компании: Контур.Продажи (бывший Компас)**, уже есть, лимит 8 000 выгрузок в месяц, **API нет**. Цикл ручной: код готовит файл со списком ИНН → загрузка в Продажи → выгрузка Excel → код склеивает (переносим `merge_batch_results_with_compass`). Контур.Фокус **не покупаем**. Вернуться к нему, если в досье понадобятся суды, финансы в динамике или связи.
- ЛПР уровня маркетолога или ecom-директора ни Продажи, ни Фокус не дают. На старте выходим на собственника или гендира (П1) и на контакты с сайта.
- Опционально: DaData (бесплатный лимит) для проверки ИНН с сайта до выгрузки в Контур.
- **Стек приложения:** ядро-пайплайн на Python + CLI + веб-интерфейс на **FastAPI**. Данные в SQLite. Сначала запускаем локально на ПК (браузер на localhost). В репо сразу кладём `docker-compose.yml` для переезда на свои серверы, когда понадобится долгий прогон или доступ команды. Десктоп-сборку (exe) не делаем.
- Коннектор Google Sheets не авторизован, поэтому пока выгружаем в Excel.
